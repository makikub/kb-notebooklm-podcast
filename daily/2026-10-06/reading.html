AIエージェントの記憶をGitで育てる

Agent Memory Repoの設計と、まだ残る承認の境界

出典付き記憶 Dreaming 運用設計

発表された仕組み

CognitionはAgent Memory Repoという公開仕様を示した。短いMEMORY.mdを入口に、MarkdownやSQLなどをリンクでたどる。メモの一行には学習元のセッションURLや追加日を添えられる。セッションは最新の記憶を読み、必要な情報を探し、学んだことを更新してGitへ反映する、と説明する。これは保存形式と想定フローであって、あらゆるチームで精度が向上したという実証ではない。

発見のきっかけとなった公式投稿は「Dreaming」を紹介した。公開仕様によれば、別の定期エージェントがセッション横断のパターンを追加し、重複の統合、古い情報の除去、出典に照らした矛盾の確認を行う。ただしページ上のローカル試行には、起動時の自動読込と定期Dreamingは含まれない。ここでその機能を実行したわけではない。

既存のKBと比べると

非公開の既存KBにある「Context Graph and Company Brain」は、知識を使う前に出典・有効期間・権限を確かめ、人間が矛盾と失効を見直す設計を重視する。Agent Memory Repoも出典付きの小さな記録とリンクを用意するが、自動整理した内容を誰が承認し、いつ共有記憶へ昇格させるかは公開仕様だけでは決まらない。これは二つの設計の比較からの推論だ。

小さく試すなら、MEMORY.mdは共通の短い目次にし、断定ごとに元セッションと記録日を残す。重複や矛盾の候補は自動で列挙しても、削除・権限変更・重要判断の上書きはレビュー待ちにする。Gitの差分は変更を見つけやすくするが、変更内容の正しさまでは保証しない。ここはCognitionの実測成果ではなく、既存KBの証拠品質の考え方からの運用提案だ。

明日の確認項目

  • 各メモから元セッションに戻れるか。出典が消えたらどう扱うか。
  • 複数エージェントの同時更新で競合をどこで止めるか。
  • Dreamingの提案と確定事実を区別し、誤更新を差分から戻せるか。
記憶を長く持つだけではKBは育たない。出典をたどり、変更を検査し、共有する前に責任の境界を置けるかが焦点になる。

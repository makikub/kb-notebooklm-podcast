# AIエージェントの記憶をGitで育てる――Agent Memory Repoの設計と未解決の境界

2026年10月6日｜Cognitionの新しい公開仕様を、出典と承認の観点から読む

## 発表された仕組み
Cognitionは「Agent Memory Repo」という公開仕様を示した。短い `MEMORY.md` を入口にし、他のMarkdownやSQLなどをリンクでたどる。各メモの一行には学習元のセッションURLや追加日をメタデータとして添えられる。セッションは最新版を読み、必要な情報を探し、学習した内容を更新してGitへ反映する、と説明する。これは保存形式と想定フローの説明であり、どのチームでも記憶の正確さが向上したという実験結果ではない。[Cognitionの仕様](https://cognition.com/agent-memory-repo)

発見のきっかけとなった[Cognitionの投稿](https://x.com/cognition/status/2107165034463867001)は「Dreaming」を紹介する。公式ページでは、別の定期エージェントがセッションを横断してパターンを追加し、重複を統合し、古い情報を除き、出典から矛盾を確認すると説明している。ただし公開ページのローカル試行は、起動時の自動読込や定期Dreamingを含まない。手元でその機能を有効にしたわけではない。[Cognitionの仕様](https://cognition.com/agent-memory-repo)

## 既存のKBと比べると
非公開の既存知識ベースにある「Context Graph and Company Brain」マップは、知識を利用する前に出典・有効期間・権限を確認し、人間が矛盾と失効を見直す設計を重視する。Agent Memory Repoも出典付きの小さな記録とリンクを用意するが、**自動整理された内容を誰が承認し、いつ共有記憶へ昇格させるか**は仕様ページだけでは決まらない。これは公開仕様とKB設計の比較からの推論だ。

実装するなら、まず `MEMORY.md` を全セッション共通の短い目次にし、個別の断定には元セッションと記録日を付ける。次に重複・矛盾の候補を自動で列挙しても、削除・権限変更・重要な判断の上書きはレビュー待ちにする。Gitの差分は「何が変わったか」を追いやすくするが、差分の正しさを保証しない。ここはCognitionの実測成果ではなく、既存KBの証拠品質マップに照らした運用提案である。

## 明日の確認項目
- 記憶の各行から元セッションへ戻れるか。元情報が消えた場合にどう扱うか。
- 複数エージェントが同じファイルを書き換えたとき、競合をどこで止めるか。
- Dreamingの提案と確定済み事実を分け、誤った整理を差分から戻せるか。

**記憶を長く持つだけではKBは育たない。出典をたどり、変更を検査し、共有する前に責任の境界を置けるかが焦点になる。**

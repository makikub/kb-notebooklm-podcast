Coding-Agent Harness Patterns for Always-On Agents

8月17日の Cursor Origin beta と、8月19日の Cloud Agents（Subscriptions / /goal / subagent VMs）は、コーディングエージェントを「一回の回答」から「起きているあいだ仕事を続けるシステム」へ寄せた。KBの8パターンは、その常時稼働を安全に走らせるための読み方になる。

2. 8パターンが製品になった計画、検証役の分離、環境起動、安いチェック、進捗の可視化、PRまでのループ、rubric、部品の選別。Cursorの1週間は、この8つをクラウドに出した。

今日のテーマは「起きていてよい形」を作ること

knowledge-base-llm の Coding-Agent Harness Patterns は、はっきりした中心命題を持っています。コーディングエージェントのワークフローは、品質と信頼性がプロンプトではなく、周囲の成果物、制御、レビュー循環に依存し始めたときに、ハーネスエンジニアリングになる。

マップ自体は Pattern 21 まで伸びています。今日は最初の8つに絞ります。2026-08-17 の Origin beta と、2026-08-19 の Cloud Agents 更新が、その8つを製品の言葉で言い直した週だからです。

Cursor changelog はこう書いています。cloud agents を改善して、always-on agents がシステムとして動き、各ループで人間が介入しなくてもソフトウェアを作って出せるようにする。イベントで仕事を拾い、目標を完了まで持ち、長いセッションでもコースを外さない。

この1週間の Cursor 角

8月17日、Origin が early beta として有料プランに出ました。repos、pull requests、コード閲覧と検索、GitHub 双方向同期が Cursor の Codebase タブに入ります。公式の整理では、GitHub から始めたものは GitHub が source of truth のまま。pushes も GitHub へ行く。agent-native な機能は「ship soon」と先送りされています。つまり今の Origin は、移行先というより、エージェントの隣に置かれたレビュー面です。

8月19日の更新は、その面の上でエージェントを常時稼働にします。Subscriptions は PR、Slack thread、scheduled tasks を監視し、何かが起きたら起きる。作った PR には自動で subscribe し、CI を直し、bot comments に返す。Slack では @cursor check back in an hour and keep going until that feedback is in と言える。

/goal は長い目標を完了まで持たせる。changelog の例は /goal fix all flaky tests and make CI green。Custom Mode は skill をピン留めする always-on skill。subagent は独立 VM で、隔離されたプロジェクトコピーと clean context を持つ。steering は今の操作を切らず、次の tool call まで待つ。

Pattern 1–2. 計画を残し、採点役を分ける

最初のパターンは、計画を会話に閉じ込めないことです。plan.md のようなセッション単位の計画は、意図を見える化し、context reset からの復帰を支え、verifier が批評できる安定した対象になります。/goal は、その計画の寿命を製品側で伸ばしたものです。ファイルに残らない /goal は、ただの長いチャットです。

二番目は verifier split です。実行役を丸ごと複製しなくてよい。計画レビューか実装レビューだけ、別のモデルや別セッションに出せば、自己採点バイアスはかなり減ります。subagent VMs は、この分離を物理的にします。親と同じ汚れを共有せず、新鮮な環境で試す。常時稼働では、同じ文脈が何時間も続くので、この分離は贅沢ではなく保険です。

Pattern 3–4. 起きる前に走らせ、安く落とす

三番目は、タスクの前に環境を走れる状態にすることです。依存が壊れている、テストが赤、起動手順が曖昧、生成物が検索に混ざる。このまま subagent を増やしても、壊れた baseline が複製されるだけです。Subscriptions は、壊れた環境を定期的に起こす機械にもなります。

四番目は、安い決定的チェックを実装のすぐ隣に置くことです。lint、hooks、pre-commit、tests。再生成が安いなら、検証も安くなければいけません。Cloud agents が CI と bot comments を追い続けるなら、その信号が安定していないと、ループはノイズを往復します。flaky な CI に /goal を向けると、エージェントは「直し続ける」が、人間は完了条件を失います。

Pattern 5–6. 進捗を残し、ローカルの外まで伸ばす

五番目は、軽い成果物で進捗を見ることです。task list、生きた spec、残件。重いスキーマは要りません。Subscriptions は「いつの間にか進んでいる」状態を作ります。朝戻ったときに読むべきは、チャット全文ではなく、更新された計画と PR の checks です。Origin の timeline と diffs は、その可視性を IDE の中に寄せます。

六番目は、ハーネスをローカル実行で終わらせないことです。commit、push、PR、autofix、自動レビュー、heartbeat。8月19日の Subscriptions は、まさにこのパターンの製品化です。Origin は、そのループが触る repo と PR をエージェントの隣に置きます。GitHub が source of truth でも、統合面でしか出ない問題を、同じ作業面で拾えるようになります。

Pattern 7–8. 意味の物差しを揃え、部品は選ぶ

七番目は、決定的チェックと共有 rubric を対にすることです。受け入れ条件、対象外、リスク、公開可否、ユーザー影響。これが無いと、常時稼働の返信は量だけ増えます。Custom Mode は焦点を固定できますが、ピン留めするものが曖昧なら、癖が always-on になります。

八番目は、生態系をカタログとして見て、作業ハーネスには小さな信頼済みセットだけを入れることです。Origin、Subscriptions、/goal、subagent VMs、Custom Modes、steering を一度に全部オンにする必要はありません。先に、計画、安いチェック、隔離された検証、PR までのループ、止める場所。常時稼働は、未整理な道具箱を一晩中振る機械にもなります。

3層で見ると、製品の置き場所が分かる

KBは制御を3層に分けています。Feedforward は plan、/goal、repo conventions、Custom Mode。In-loop は hooks、Subscriptions、steering、task list、subagent VMs。Feedback は lint、tests、PR review、autofix、人間の accept / reject。

Cursor の1週間は、この3層をクラウドへ伸ばしました。だからニュースの核は「賢いモデルが常時動く」ではありません。「3層がイベントで起きる」。速く回してよい層と、人間が止める層を分けたときだけ、always-on は複利になります。

マップ後半の rule-update loop や harness owner、manager-subagent fleet は、この8つが回ってから効きます。常時稼働は、その順番を飛ばす誘惑を強くします。今夜エージェントを起きていてよいなら、まず完了条件と安いチェックと停止ゲートをファイルに置いてからにしてください。

よい always-on 運用は、強いプロンプトを常時オンにすることではない。計画で入口を作り、安い検証で心拍を取り、検証役を分け、PRの外までループを伸ばし、繰り返す失敗だけを次回のルールに戻す。

次に考えるとよさそうな問い

  • 今夜エージェントを起きていてよいイベント源は、PR、Slack、スケジュールのどれか？
  • /goal の完了条件は、CI 緑だけか。rubric 上の意味も含むか？
  • subagent に渡す前に、どの環境チェックが必須か？
  • Origin をレビュー面として使うとして、source of truth はどこに残すか？
  • 繰り返している指摘を、どのテスト、skill、hook に昇格させるか？
  • 人間だけが止めるべき変更は、どれか？

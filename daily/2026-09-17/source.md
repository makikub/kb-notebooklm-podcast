## なぜセッション監視と Agent Anomaly Detection が部品になるか

- 同じ「点検」でも、指標評価と、セッションの二度目の目は、支えが違う
- 同じ「安全」でも、帯域外の監視と、実行中の門は、効く位置が違う
- 同じ「検知」でも、統計と、推理と、再構成は、機械が違う
- 同じ「止める」でも、発見と、次の道具の停止と、推奨の門は、段が違う
- 同じ「方針」でも、OWASP の四項と、coming soon の社内論理は、棚が違う

KBの言葉では、ゲートは出荷後のトレースを見、承認は梯子の段を先に名指し、制御はいつ効くかとどう効くかを分け、評価は作ったエージェントの最後の一目ではない。Google の Anomaly Detection 公式は、帯域外で遅延を足さないことと、既存のログ／OpenTelemetry と、OWASP の四項と、三層のパイプラインと、Inventory の Critical／95% と、SCC と ADK callback を、一次で固定する。カスタム論理は coming soon のまま残す。ChatGPT Ads を aside に留め、Zero-trust の三つと Live 音声を核にせず、9/16 と 9/15 を一行に残し、無いライブ地図を空欄のまま残す。

Agent Harness Control Taxonomy for Editable Harnesses

Talking points（3〜5分）

  1. 公式の製品 changelog は静かだ。今日のニュースは新モデルではなく、誰がハーネスを編集できるかである。
  2. Claude Code がより hackable になる（Agents.MD と system prompt の改変）は、context harness / before-action がユーザー所有になる話だ。
  3. OpenAI のチーム/中小企業向け Pro 相当 $100（ChatGPT/Work/Codex + SSO）は、identity と組織境界という safety harness の話だ。
  4. hackable を「ガードレール」一語に潰すと、いつ効く制御か、どう効く制御かが消える。
  5. Anthropic の $5M wellbeing eval grants は evaluation harness の一行。主題は、編集可能な面が増えたあと、何を決定的制御として残すかである。

今日の読み方

knowledge-base-llm の Agent Harness Control Taxonomy は、ハーネス工学の語彙を揃えるための短い地図である。「ガードレール」という言葉は便利だが、中身が違う機械を一つに潰す。このマップは、いつ効くか（行動の前、途中、後）と、どう効くか（決定的か、推論的か）を分けてから、評価・実行・文脈・安全という範囲を重ねる。

昨日までの読み物は、実装前のレビュー規準、常時稼働のパターン、KB＋コードベースのオンボーディングだった。今日は制御の分類そのものに戻る。理由は、公式の製品 changelog が静かでも、編集可能な面の話が出ているからだ。製品面が静かな日に見えるのは、誰がどの層を触ってよいかである。

X では、Anthropic 社員の trq212 が、Claude Code はより hackable になると書いている。Agents.MD と system prompt の改変が来る、と。OpenAI の Tibo は、チームや中小企業向けに Pro 相当の $100 プランを出し、ChatGPT / Work / Codex と SSO を載せる、と書いている。どちらも「もっと賢いモデル」ではない。「誰が文脈面を編集でき、誰が組織の境界を持つか」である。Anthropic 公式は 8/25、$5M の wellbeing eval grants を出したが、今日の主題は taxonomy のままである。

今日の問いは「新しいプロンプトをどう書くか」ではない。「編集可能になった面を、どの軸の制御として扱うか」である。

1. 二つの軸 — いつ効くか、どう効くか

ハーネス制御は、二つの実務軸に沿う。

  1. いつ効くか — 行動の前、行動の途中、行動の後
  2. どう効くか — 決定的 / 計算的か、意味的 / 推論的か

この二つは排他ではない。同じ hook が、実行中の介入にも、文脈の注入にも、安全境界にもなりうる。だから「ガードレールを足した」では、比較できない。

なぜ効くか:

  • 比較できない語彙は、導入の議論を感想にする
  • いつ効くかが分からないと、失敗の責任も分からない
  • どう効くかが分からないと、コストと信頼を見誤る

今日の角:
Agents.MD と system prompt の改変は、まず「いつ」では before-action、「範囲」では context harness である。SSO 付きのチームプランは、まず safety harness である。同じ「hackable」でも、軸が違う。

対話の種:
「今足そうとしているものは、行動の前に効くのか、途中か、後か。決定的か、推論的か。」

2. 範囲の四分割 — 評価、実行、文脈、安全

ソースが「ハーネス」と言うとき、機械が違うことがある。

  • Evaluation harness: モデルや提出物を採点する基盤。lm-evaluation-harness や SWE-bench 型の grader
  • Runtime harness: 推論、ツール、観察、状態、再試行を交替させるエージェントループ
  • Context harness: 指示、ルールファイル、記憶、検索、ツール、hook、skill、MCP、モデルに見える他の文脈面
  • Safety harness: sandbox、権限境界、承認フロー、identity、監査ログ、外からかけるリスク制御

これらの範囲は、タイミング軸と交差する。hook は中身次第で、実行中の制御にも、文脈注入にも、安全境界にもなる。

memory-skill の見方は、context harness を鋭くする。skill は手続き記憶である。記憶は、その手続きを経路づけ、拘束し、改訂できるときだけ役に立つ。

今日の角:
trq212 の hackable は、主に context harness がユーザー編集可能になる話だ。Tibo の SSO は、safety harness を中小企業まで製品化している。8/25 の wellbeing grants は、evaluation harness を外部に開く一行である。三つを「AI安全」にまとめると、どこを編集してよいかが消える。

対話の種:
「この変更は、採点基盤か、ループか、文脈面か、安全境界か。一つに決まらないなら、混ぜている。」

3. Before-action — 今日のニュースの中心

行動前の制御は、意味のある一歩の前に軌道を形作る。

典型:

  • タスクの範囲と分解
  • リポジトリマップ、計画、アーキテクチャ文書
  • 承認ポリシーと、使ってよいツールの境界
  • テンプレート、skill、初期化成果物
  • 段階的な文脈ロードと検索ルール

なぜ効くか:

  • 最初の一歩が、すでに近い場所から始まる
  • 編集可能な面は、ここが増える
  • 前で狭めないと、途中と後の制御が全部を引き受ける

今日の角:
Agents.MD は、会話に消える指示ではなく、リポジトリに残る before-action の契約である。system prompt の改変は、さらに強い feedforward になる。hackable の利点は、現場が文脈面を自分の言葉にできることだ。代償は、誰でも軌道を曲げられることだ。だから編集可能にするなら、何を書いてよいか、何を deterministic な境界の外に出さないかを先に決める。昨日のレビュー規準は、この前段階の文章を採点する道具だった。今日の taxonomy は、その文章がどの層かを名指す。

対話の種:
「Agents.MD に書いてよいことと、権限やテストに残すべきことは、一文で分かるか。」

4. In-loop — 編集した面が走り始めてから

実行中の制御は、エージェントがすでに動いているあいだに介入する。

典型:

  • モデル呼び出しやツール呼び出しのまわりの middleware hook
  • ループ検出と予算ヒューリスティック
  • 完了前に走る評価プロンプト
  • いまの状態に応じた動的な文脈注入
  • 危ない遷移での人間チェックポイント
  • 実行中に stop / redirect ファイルを出す操作者の操舵

なぜ効くか:

  • ドリフトは、終わってからより途中の方が安い
  • 編集された Agents.MD は、ループの中で増幅される
  • 途中の介入は、モデルを変えずに軌道を戻せる

今日の角:
system prompt をユーザーが触れるようになると、in-loop の hook が「隠れた第二の system prompt」になりやすい。hackable のつもりが、見えにくい middleware の積み上げになる。操舵ファイルや予算、完了前の評価は残してよい。ただし、それは context harness のコピーではない。実行中に効くものと、行動前に残すものを分ける。

対話の種:
「走り始めてから効く制御は、編集可能な指示ファイルと役割が重なっていないか。」

5. After-action — 編集を信頼しない層

行動後の制御は、一歩のあとに、出力、環境、本番の振る舞いを見る。

典型:

  • テスト、lint、構造チェック
  • AI レビューや、別の評価エージェント
  • 証拠と主張の対応、claim ledger
  • スクリーンショットやログを開くまで status を更新しない evidence gate
  • デプロイゲート、rollback、可観測性
  • トレースレビューと、定期的な掃除

なぜ効くか:

  • 文脈面は嘘をつける。テストは嘘をつきにくい
  • hackable なほど、後の決定的チェックが本体になる
  • 改善のフィードバックは、後からシステムへ戻る

今日の角:
公式の大型ドロップが無い日でも、編集可能な面は増える方向にある。だから after-action を「レビューの礼儀」にしない。Agents.MD をどれだけうまく書いても、テストが赤なら失敗である。wellbeing eval grants は、この層の評価版を、製品の外に開く話だ。今日は深く入らない。評価基盤と実行ループを混ぜない、とだけ覚える。

対話の種:
「文脈面を誰が編集しても、赤なら止める決定的チェックはどれか。」

6. 決定的か、推論的か

Martin Fowler の分け方が、いまのKBで一番きれいである。

決定的 / 計算的:

  • 構造テスト、lint、スキーマ、命名や配置のルール、硬い承認境界
  • 強い点: 繰り返しが安い、信頼しやすい、同じ失敗を曖昧にしない
  • 弱い点: 意味や好みには脆い。測れるものだけが最適化される

推論的 / 意味的:

  • 評価エージェント、AI レビュー、rubric 採点、完了や UX のモデル判定
  • 強い点: ニュアンスに届く。主観や開いた課題に合う
  • 弱い点: 高くてノイズが多い。評価役のドリフトと自己採点バイアス

今日の角:
Agents.MD と system prompt は、それ自体が推論的制御の入力である。モデルが読む文章を増やしても、決定的境界は増えない。SSO は逆で、identity という決定的な安全境界を、小さい組織にも配る。hackable な文脈面と、決定的な安全面は、同じ「プラン」には載っても、同じ制御ではない。

対話の種:
「いま足している文章は、モデルへの入力か。機械が同じ結果を返す境界か。」

なぜ分類が部品になるか

  • ソース同士を、同じ語彙で比較できる
  • 編集可能な面を足すとき、どの層を開いているか言える
  • 決定的チェックがあるのに、推論的レビューだけを足さない
  • モデルが自分で担えるようになった制御を、外す判断ができる

KBの言葉では、これは feedforward、middleware、feedback を、範囲（評価 / 実行 / 文脈 / 安全）と交差させる地図である。昨日の6軸 rubric は推論的制御の採点台本だった。今日の taxonomy は、その台本をどの層に置くかの棚である。

今日の X の型は、context harness をユーザーに開き、safety harness をチームプランに載せる。公式の大型更新が無い日に見えるのは、その開閉である。

トレードオフ

強い before-action は、最初の一歩を近づけるが、エージェントを縛りすぎる。弱い before-action は、後段の修正に全部を預けてしまう。middleware はモデルを変えずに済むが、振る舞いの説明が難しくなる。決定的チェックは安いが、意味を落とす。推論的チェックは意味に届くが、高くて漂う。

だから今日の使い方は、分類を増やすことではない。編集可能になる面を context / before-action と名指し、SSO と権限を safety に残し、テストと lint を after-action の決定的層に残す。評価助成は、評価基盤の話として横に置く。

実務のとりはじめ

大きな基盤は要らない。今日からできる最小セット:

  • Agents.MD や system prompt に書く前に、それが before-action / context だとラベルする
  • 権限、SSO、sandbox は、プロンプトに落とさず safety に残す
  • 編集した文脈面が走り始めたら、予算・操舵・完了前チェックを in-loop に置く
  • テスト、lint、スキーマは、誰が指示を書いても赤なら止める
  • 推論的レビューは、決定的チェックの隣に置く。代わりにはしない

昨日の rubric は、計画を6軸で焼く話だった。今日の taxonomy は、焼いた計画や編集した指示が、どの棚の制御かを固定する話である。公式が静かな日は、棚の名前を先に固定する日になる。

次に考えるとよさそうな問い

  • 今の Agents.MD は、before-action か。それとも実行中の第二の system prompt か？
  • system prompt を誰が改変してよいか。リポジトリの契約か、個人の好みか？
  • SSO と権限は、文脈面から分離されているか？
  • 文脈面を誰が編集しても、赤なら止める決定的チェックはどれか？
  • 推論的レビューを、決定的チェックの代わりに使っていないか？
  • モデルが自分で担えるようになった制御を、外す規則はあるか？

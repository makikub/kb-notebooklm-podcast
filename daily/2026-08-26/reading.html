今日のテーマは「編集可能な面」を分類すること

knowledge-base-llm の Agent Harness Control Taxonomy は、ハーネス工学の語彙を揃える短い地図です。「ガードレール」は便利ですが、中身が違う機械を一つに潰します。このマップは、いつ効くか（行動の前、途中、後）と、どう効くか（決定的か、推論的か）を分けてから、評価・実行・文脈・安全という範囲を重ねます。

昨日までの読み物は、実装前のレビュー規準、常時稼働のパターン、KB＋コードベースのオンボーディングでした。今日は制御の分類そのものに戻ります。公式の製品 changelog が静かでも、編集可能な面の話が出ているからです。製品面が静かな日に見えるのは、誰がどの層を触ってよいかです。

X では、Anthropic 社員の trq212 が、Claude Code はより hackable になると書いています。Agents.MD と system prompt の改変が来る、と。OpenAI の Tibo は、チームや中小企業向けに Pro 相当の $100 プランを出し、ChatGPT / Work / Codex と SSO を載せる、と書いています。どちらも「もっと賢いモデル」ではありません。「誰が文脈面を編集でき、誰が組織の境界を持つか」です。Anthropic 公式は 8/25、$5M の wellbeing eval grants を出していますが、今日の主題は taxonomy のままです。

ニュースはモデルではなく、開閉である

hackable を「もっとプロンプトを書ける」と読むと、軸が消えます。Agents.MD は、会話に消える指示ではなく、リポジトリに残る before-action の契約です。system prompt の改変は、さらに強い feedforward になります。利点は、現場が文脈面を自分の言葉にできることです。代償は、誰でも軌道を曲げられることです。

だから編集可能にするなら、何を書いてよいか、何を決定的な境界の外に出さないかを先に決めます。権限、SSO、sandbox は safety harness です。テスト、lint、スキーマは after-action の決定的層です。昨日のレビュー規準は、この前段階の文章を採点する道具でした。今日の taxonomy は、その文章がどの層かを名指します。

Tibo のチームプランは、identity という決定的な安全境界を、小さい組織にも配ります。同じ「プラン」に ChatGPT / Work / Codex が載っても、SSO は文脈面ではありません。8/25 の助成は evaluation harness を外部に開く一行です。今日は深く入りません。評価基盤と実行ループを混ぜない、とだけ覚えます。

四つの範囲は、同じ「ハーネス」ではない

ソースがハーネスと言うとき、機械が違います。Evaluation は採点基盤。Runtime は推論とツールと再試行のループ。Context は、モデルに見える指示、ルール、記憶、skill、MCP。Safety は、外からかける権限と監査です。

hook は中身次第で、実行中の制御にも、文脈注入にも、安全境界にもなります。memory-skill の見方は、context を鋭くします。skill は手続き記憶です。記憶は、その手続きを経路づけ、拘束し、改訂できるときだけ役に立ちます。

trq212 の hackable は、主に context がユーザー編集可能になる話です。Tibo の SSO は、safety を中小企業まで製品化しています。wellbeing grants は、評価を外に開く話です。三つを「AI安全」にまとめると、どこを編集してよいかが消えます。

走り始めてからと、終わってからを混ぜない

system prompt をユーザーが触れるようになると、in-loop の hook が「隠れた第二の system prompt」になりやすい。hackable のつもりが、見えにくい middleware の積み上げになります。操舵ファイルや予算、完了前の評価は残してよい。ただし、それは context harness のコピーではありません。

after-action を「レビューの礼儀」にしないでください。文脈面は嘘をつけます。テストは嘘をつきにくい。Agents.MD をどれだけうまく書いても、テストが赤なら失敗です。公式の大型ドロップが無い日でも、編集可能な面は増える方向にあります。だから決定的チェックが本体になります。

Fowler の分け方が、ここでききます。Agents.MD と system prompt は、それ自体が推論的制御の入力です。モデルが読む文章を増やしても、決定的境界は増えません。SSO は逆です。hackable な文脈面と、決定的な安全面は、同じ制御ではありません。

増やさず、棚の名前を固定する

強い before-action は、最初の一歩を近づけますが、エージェントを縛りすぎます。弱い before-action は、後段の修正に全部を預けます。middleware はモデルを変えずに済みますが、振る舞いの説明が難しくなります。決定的チェックは安いが、意味を落とします。推論的チェックは意味に届くが、高くて漂います。

だから今日の使い方は、分類を増やすことではありません。編集可能になる面を context / before-action と名指し、SSO と権限を safety に残し、テストと lint を after-action の決定的層に残します。推論的レビューは、決定的チェックの隣に置きます。代わりにはしません。

昨日の rubric は、計画を6軸で焼く話でした。今日の taxonomy は、焼いた計画や編集した指示が、どの棚の制御かを固定する話です。公式が静かな日は、棚の名前を先に固定する日になります。

よい hackable 化は、system prompt を誰でも触れるようにすることではない。Agents.MD を before-action / context と名指し、権限と SSO を safety に残し、誰が指示を書いても赤なら止める決定的チェックを after-action に残す。

  • SSO と権限は、文脈面から分離されているか？

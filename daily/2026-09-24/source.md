## 1. 三つの判定は、一つの緑ではない

changelog は、環境ごとの変更の健康を、三つの名前で書く。verified healthy。regression detected。inconclusive。三つは、一つの「大丈夫」ではない。inconclusive は、健康の別名ではない。回帰の別名でもない。検証できなかった、という第三の判定である。

KBの出荷後の層は、可観測性、回帰検出、トレースレビュー、ドリフトの掃除、である。Rollouts は、その層に、変更ごとのモニタを付ける、と読める。起きるのは、その変更のコミットのデプロイイベントである。計画を、ログ、メトリクス、トレースに対して走らせる。意図した効果を、エラーとレイテンシのシグナルと並べて見る。判定に達したら、PR に報告する。

環境は別々である。changelog が書く例は、staging で検証済みでも、production では旗が付いたまま、でありうる、である。staging の healthy を、production の healthy に昇格させない。環境の一覧を、staging と production の二つに限定もしない。本文が固定するのは、別々に追うことと、その例である。無い canary の百分率を invent しない。

なぜ効くか:
- inconclusive を healthy にすると、検証できなかった変更が緑になる
- staging の healthy を全体の healthy にすると、production の旗が消える
- エラーとレイテンシだけを見ると、意図した効果の確認が消える
- 判定前の監視を、判定そのものにすると、PR に戻る報告が消える

## 2. 計画は、デプロイの前に残るコメントである

PR が開くと、Rollouts は差分と、触るシステムを読む。モニタリング計画を、PR コメントとして書く。中身は四つである。見つけたリスク。変更が持つはずの効果。見るシグナル。検証を難しくする計装の隙間。PR 上で計画を編集すると、Rollouts はその版を使う。

KBのいつ効くかは、前、途中、後、である。計画コメントは、デプロイの前に残る。判定は、デプロイイベントのあとである。同じ bot でも、段が二つある。計画を、すでに出た判定として読まない。判定を、まだ編集できる計画として読まない。

編集は、計画の所有者を人に戻す。changelog は、編集した版を使う、と書く。編集しなかった計画が、そのまま走ることと、編集した版が走ることとは、同じ「自動」ではない。人が直した文は、bot の下書きではない。

計装の隙間は、計画の四番目である。検証を難しくする、と changelog が書く。inconclusive という判定の名前とは、別の文である。隙間の列挙を、inconclusive の件数にしない。ブログが、欠けた計装を、見逃しの最も一般的な理由、と書いても、率は無い。changelog の隙間を、その「最も一般的」で埋めない。

なぜ効くか:
- 計画コメントを判定にすると、デプロイ前の下書きが健康になる
- 編集を無視すると、人が直した版が消える
- 隙間の列挙を inconclusive の件数にすると、無い率が生まれる
- リスクと、意図した効果と、シグナルと、隙間を、一つの「見ておく」にすると、四つの欄が消える

## 3. 回帰の次手は、通知と、レビューに残る戻しである

KBの承認は、広い権限を二値のスイッチにするな、と書く。段は、自動許可、助言レビュー、完了を塞ぐレビュー、人間だけ、である。今日の revert PR は、レビュー用である。開くことは、戻し終えることではない。cloud agent への引き渡しは、直すため、である。その修正を誰がマージするかは、changelog が書かない。無い自動マージを invent しない。自分でマージしない、という文は、Rollouts の文である。cloud agent のその後を、同じ文で埋めない。欠けを名指す。

today を落とすと、文が恒久の製品境界になる。today を、来月の日付に換算もしない。ページが書くのは、今日は自分で戻さない、である。

なぜ効くか:
- 通知をロールバックにすると、著者への知らせが戻しの完了になる
- レビュー用の revert PR を、マージ済みの戻しにすると、for review が消える
- cloud agent への引き渡しを、修正のマージにすると、書いていない承認が生まれる

## 5. 一つのコメントは、スタイルのレビューでも、マージの門でもない

Security Review は、コードベースの文脈で pull request を読み、悪用できるバグを報告するコメントを一つ書く。スタイルと品質は Bugbot に残る。見たいリポジトリだけ、ダッシュボードで有効にする。draft は飛ばす。

KBのレビュー負荷は、エージェント速度の本当の上限、と書く。一つのコメントは、その負荷を、悪用に狭めた形である。スタイルの指摘を、このコメントへ移さない。Bugbot を、このコメントの別名にしない。二つのレビューが残る、と changelog は書く。一つに潰さない。

探す範囲は、changelog が列挙する。SQL、コマンド、テンプレートのインジェクション。認証と認可の迂回。リファクタで止まった検査を含む。ソースに入った秘密と資格情報。SSRF と未検証のリダイレクト。安全でないデシリアライズ。既知の脆弱性を入れる依存の変更。利用者の入力がどこから入り、何を通過するか。この一覧を、ブログの LDAP と、インフラの安全でない既定で、伸ばさない。ブログが足す項目は、ブログの項目である。changelog の一覧を、そちらで完成させない。

発見の中身は三つである。重大度。攻撃経路。提案する修正。提案は、適用済みではない。ブログの one-click fix は、changelog の「提案する修正」を、押したあとのマージにしない。理由を付けて却下すると、その PR ではもう上げない。却下は、その PR の中の話である。リポジトリ全体の永久除外とは書いていない。無い全社の記憶を invent しない。

チーム規則は、例が二つである。外部呼び出しが通らねばならないクライアント。リクエストハンドラから決して問い合わせない表。すべての PR で効かせる、と書く。例を、規則の全集にしない。

changelog は、このコメントがマージを塞ぐ、とは書かない。必須のステータスチェックとも書かない。助言のコメントとして置ける範囲と、完了を塞ぐレビューとして置ける範囲は、承認の地図では別の段である。今日の本文は、どちらの段かを名指さない。塞ぐ、と補わない。欠けを名指す。draft を飛ばす、は書いてある。draft 以外は全部見る、と、有効にしたリポジトリの中では読める。有効にしていないリポジトリまで広げない。

なぜ効くか:
- 一つのコメントにスタイルを足すと、Bugbot の残り仕事が消える
- draft をレビュー対象にすると、飛ばす、が消える
- 提案する修正を、マージ済みの修正にすると、one-click が changelog になる
- LDAP を changelog の一覧に足すと、ブログが制約を増やす
- コメントをマージの門にすると、書いていない遮断が生まれる
- 一つの PR の却下を、全社の記憶にすると、本文の範囲が消える

今日の角:
見出しは Security Review である。Get started は Security Reviewer と書く。二つの綴りは、同じページにある。どちらかを誤記として消さない。ブログの箇条は「見つけ、直す」である。changelog は「報告するコメントを一つ」である。直す、を、コメントの中の提案に留める。適用の主体を、Rollouts の「自分ではマージしない」から切り離す。Security Review が自分でマージする、とも、しない、とも、changelog は書かない。Rollouts の文を、Security Review のマージ権限に流用しない。欠けは、欠けのまま置く。

対話の種:
「今日のセキュリティは、一つの悪用コメントか。Bugbot のスタイルか。マージを塞ぐチェックか。」

## なぜ判定の名前が部品になるか

- 同じ「健康」でも、verified healthy と、inconclusive と、staging の健康を production に写したものは、判定が違う
- 同じ「計画」でも、リスク、意図した効果、シグナル、計装の隙間は、欄が違う。編集前と編集後も違う
- 同じ「戻す」でも、著者への通知、レビュー用の revert PR、cloud agent への引き渡し、自分で終えたロールバックは、権限が違う
- 同じ「50」でも、roughly 50 changes と、ドルと、Security Review の枠は、単位が違う
- 同じ「レビュー」でも、一つの悪用コメントと、Bugbot のスタイルと、マージを塞ぐチェックは、段が違う
- 同じ「直す」でも、発見の中の提案と、one-click と、適用済みのマージは、状態が違う
- 同じ「あとから見る」でも、環境ごとのデプロイと、9/17 のセッションと、音声生成は、対象が違う

KBの言葉では、出荷後は回帰とトレースを見る層であり、制御は前と後を分け、レビュー負荷は速度の上限であり、評価は作った本人の最後の一目ではない。changelog は、三つの判定、編集できる計画コメント、環境が分かれること、自分ではマージもロールバックもしないこと、一つの悪用コメント、draft を飛ばすこと、roughly 50 と roughly 500 changes、を一次で固定する。ブログの戻す、直す、止めたロールアウト、one-click、LDAP、トレインは、その制約を増やす材料にしない。TTS の $9 と $6 は、音声生成の aside に留める。無いライブ地図を空欄のまま残す。

## トレードオフ

inconclusive を healthy にすると、検証できなかった変更が緑になる。staging の健康を production に写すと、旗が消える。計画コメントを判定にすると、デプロイ前の下書きが健康になる。編集を無視すると、人が直した版が消える。通知をロールバックにすると、知らせが完了になる。レビュー用の revert PR をマージ済みにすると、for review が消える。cloud agent への引き渡しを修正のマージにすると、書いていない承認が生まれる。止めた段階的ロールアウトを changelog に足すと、ブログが次手の一覧を増やす。roughly を外すと、およそが正確な件数になる。50 changes をドルにすると、無い単価が生まれる。一つのコメントにスタイルを足すと、Bugbot が消える。提案を one-click の適用にすると、コメントがマージになる。LDAP を一覧に足すと、ブログが探す範囲を完成させる。コメントをマージの門にすると、書いていない遮断が生まれる。書いた速さと、トークン効率と、TTS の $9 を核にすると、三つの判定が消える。9/23 の梯子と、9/17 のセッションと、9/16 の Live を再審すると、今日の環境ごとの健康が、昨日の核の続きになる。無い率と、無い終了日と、無い wiki 本文を埋めると、無い測定が生まれる。

だから今日の使い方は、地図を増やすことではない。判定の名前を残す。healthy と regression と inconclusive を混ぜない。環境を混ぜない。計画と判定を混ぜない。通知と、レビュー用の戻しと、自分で終えたロールバックを混ぜない。一つの悪用コメントと、Bugbot と、書いていないマージの門を混ぜない。ブログは、changelog の制約の外に置く。

1. 四段階 — 今日の一次は Tier 1

KBは証拠を四段階に置く。

  1. Tier 1: Direct primary evidence — 公式ドキュメント、ソースリポジトリ、手法の見える論文、再現できる例。定義、製品の振る舞い、硬い制約に使う。信頼は高い。ただし取得が部分的か古いときは落とす
  2. Tier 2: Practitioner operational evidence — 一人称の運用報告、ポストモーテム、実装ノート。この場でこの型が動いた、には中〜高。一般化には低い
  3. Tier 3: Public synthesis and commentary — X スレッド、ポッドキャスト要約、二次のまとめ、製品発表の弱い読み。語彙と手がかり。核の主張を一人で支えてはいけない
  4. Tier 4: KB synthesis — 地図、比較ノート、耐久回答。信頼は引用に依存する。依拠したソースを見せる

なぜ効くか:

  • 同じ文でも、段が違えば再利用の範囲が違う
  • 段を混ぜると、公式の制約と噂の隙間が同じ太さになる
  • 新しい一次ページは、新しいモデルではなく、核を載せ替えてよい合図になる

今日の角:
地図は product announcements を Tier 3 に置くことがある。今日の OpenAI ページは、機能発表の弱い読みではない。会社が硬い制約を書いた公式の決定文である。Tier 1 の「official docs」と「hard constraints」に載せる。ヘルプ記事も同じ段の公式ドキュメントである。この読み物自体は Tier 4 の合成であり、依拠は二つの一次 URL に限る。

対話の種:
「いま書こうとしている文は、Tier 1 のどの URL が支えているか。それとも、発表を要約した二次か。」

2. ページが支えること、支えないこと

ソースノートの型は、Source type、Confidence、Supports、Main limitations、Best use である。今日の決定文に当てると、型が先に決まる。

  • Source type: 公式の会社決定文（openai.com/index）
  • Confidence: ページが書いた範囲では高い。取得は今ランで確認した
  • Supports: SpaceX への通知、契約の巻き戻し、提案の遮断日 11/12、最長通知、支配権変更の解除窓、Astra を渡さない、ToS への自信の欠如、Twitter/X の契約違反、xAI の宣誓、約4年の提携、影響を受けるのは開発者
  • Main limitations: 一方の当事者の文である。終了日の双方確定は書いていない。Astra の仕様は書いていない。Cursor の応答は書いていない
  • Best use: 硬い制約の定義。製品の振る舞いの一般論や、発射記録には使わない

ヘルプ記事は同じ会社の別ノートである。

  • Source type: 公式ヘルプ（help.openai.com）
  • Confidence: 運用境界の記述では高い
  • Supports: 移行期間としての 11/12、そのあいだ現在のモデルアクセスを続ける、Cursor がより早く切る可能性、公式終了日は両社確定待ち、BYOK はローカル Chat/Agent のみ、Codex 拡張は別エージェント、Tab/Auto/Cloud/CLI/API/SDK は Cursor 供給、gateway/Bedrock/Azure はローカル経路
  • Main limitations: 「directional」であり、Cursor 側が機能を変える可能性を自ら書いている。Cursor 公式ドキュメントを最新とせよ、とも
  • Best use: 製品の振る舞いと、終了日が未確定であることの定義

関係語は短い。決定文は巻き戻しの通知を supports する。ヘルプは運用境界でそれを extends する。両者は contradicts しない。提案の 11/12 と、公式終了日は未確定、は同じ会社の二つの一次であり、混ぜると「11/12 に切れる」という別の文になる。この読み物は両方に depends_on する。

今日の角:
「Cursor は今日モデルを失った」は、どちらのページも支えない。アクセスは、提案の 11/12 まで続くとヘルプが書く。それより早く切る権限は Cursor 側にある、とも書く。確定日はまだ無い。Astra の仕様を、渡さないという一文から足すこともできない。

対話の種:
「11/12 は提案か。確定か。Astra について、ページが支えているのは名前と非提供か。仕様か。」

3. 不在は証拠である

地図は、弱い信号を核に載せない、と書く。今日の弱い信号は、噂のスレッドではない。Cursor 側の一次ページが、まだ無いことである。

Cursor.com の changelog の先頭は、8/27 の Start from scratch のままである。blog にも、8/28 の決定への応答は無い。2026-08-31 時点で、一次応答は観測されていない。これは「Cursor が同意した」でも「隠している」でもない。一次文が無い、という負の記録である。

4. Claim source と Discovery source

公開文にするとき、地図は二つの出自を分ける。Claim source は、事実の文を直接支える一次である。Discovery / posting source は、その一次を KB に運んだ経路である。X 由来なら、投稿者、URL、投稿時刻、取得時刻、リンク先の一次 URL を残す。

今日の Claim source は二つである。openai.com の決定文と、help.openai.com の運用記事。Discovery source は、今ランの公式ウォッチである。X bookmarks は 0 なので、X を発見経路にも核にもしない。投稿ハンドルを足して、公式文の重みを増やさない。

タイのスタートアップ、教育、ブラジルの投稿は、同じ日の OpenAI 面にある。薄い。今日の決定文を supports しない。同じドメインでも、ページが違えば支えが違う。Omni 1.1 Flash の公式ブログは、動画 API の Claim source になり得る。主題の Claim source にはならない。一行で止める。

今日の角:
「OpenAI が書いた」は、出自の全部ではない。どの URL の、どの文が、どの主張を支えるかである。決定文を、ヘルプの BYOK 境界の代わりに使わない。ヘルプを、Astra 非提供の代わりに使わない。Omni のブログを、供給契約の代わりに使わない。

対話の種:
「この文の Claim source はどれか。Discovery の X や二次報道を、Claim に昇格させていないか。」

5. Companion は制約の定義である

Tier 1 は、製品の振る舞いと硬い制約に使う。ヘルプ記事が定義するのは、残る経路の形である。ローカル Chat/Agent の BYOK。Codex 拡張という別エージェント。gateway / Bedrock / Azure というローカル経路。残らない面も定義する。Tab、Auto、Cloud、Background Agents、Automations、CLI、API、SDK は、Cursor が供給または経路するモデルであり、利用者が持ち込んだ OpenAI キーでは動かない。

これはハーネス地図の続きではない。今日の読みは、ヘルプがどの振る舞いを定義し、どの振る舞いを「Cursor が変えるかもしれない」と留保したかである。記事自身が directional と書く。最新は Cursor 公式ドキュメントを見よ、とも。一次であっても、キャプチャの鮮度と、相手側が変える余地を、Main limitations に残す。

決定文は Astra を渡さない、と書く。仕様、日程、性能は書かない。名前と非提供だけが supports される。未来モデルのゲートを、未公開の仕様で埋めると、Tier 1 を超える。

今日の角:
「全部のモデルが今日消えた」は、ヘルプが否定する。いまのアクセスは続く。切れる日は、提案の 11/12 か、Cursor がより早く切る日か、両社が後で確定する日か、の三つの文がある。一つに潰すと、ページが支えていない確定日が生まれる。

対話の種:
「BYOK が届く面は、Chat/Agent か。Tab か。Cloud か。公式終了日を、提案の 11/12 と書いていないか。」

6. 二次と薄い投稿を核に載せない

地図の Tier 3 は、語彙と手がかりである。核の主張を一人で支えてはいけない。今日、二次の IPO や買収報道は使わない。OpenAI の決定文が支配権変更に触れているので、買収そのものを二次から足す必要は無い。薄い投稿（タイ、教育、ブラジル）も、同じ日の公式面でも核にしない。

X bookmarks が 0 であることは、現場の声が無いことではない。今ランのブックマーク取得が空だった、という記録である。空の取得を、「誰も書いていない」に一般化しない。一般化は Tier 2 ですらない。

なぜ段が部品になるか

  • 同じ出来事でも、Tier 1 の文と Tier 3 の文は再利用の範囲が違う
  • 一方の公式文と、相手の沈黙と、取得失敗を、同じ「事実」に潰さない
  • 提案日と確定日、名前と仕様、不在と声明を、混ぜない
  • 発見経路の X を、Claim source に昇格させない

KBの言葉では、主張の強さと出自を先に書く地図である。昨日までのハーネス列は、周辺の層が性能を決める話だった。今日は、公式の二枚がどの文を支えて、どの文を支えないかの話である。公式の型は、巻き戻しの通知と提案の 11/12 を一次で固定し、確定終了日と Astra 仕様と Cursor の応答を、まだ空欄のまま残す。

トレードオフ

Tier 1 だけに寄せすぎると、運用の感触が消える。今日はそれでよい。相手の一次が無い日に、感触を二次で足すと段が崩れる。沈黙を同意に読むと速いが、無い文を足す。沈黙を隠蔽に読むと物語になるが、ページが支えない。11/12 を確定にすると予定が立つが、ヘルプが否定する。Astra の名前から仕様を足すと具体になるが、一次を超える。SpaceX.com の取得失敗を「発射なし」にすると完結するが、キャプチャの失敗を事実にする。

だから今日の使い方は、地図を増やすことではない。決定文とヘルプを Claim source と名指し、Cursor の不在を不在のまま残し、Omni を一行に残す。ハーネス列の続きにはしない。二次の買収報道にはしない。

実務のとりはじめ

  • 決定文とヘルプに、Source type / Confidence / Supports / Limitations を一文ずつ書く

  • Cursor.com を「2026-08-31 時点で一次応答なし」と日付付きで記録する
  • Omni は動画面の一行、タイ・教育・ブラジルは薄い、と別記録にする
  • X=0 を、現場の沈黙ではなく、今ランの取得空として書く
  • 二次の IPO/買収報道を、一次の穴埋めに使わない

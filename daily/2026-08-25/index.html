Coding-Agent Review Rubric Against Design Drift

  • Date: 2026-08-25
  • Theme slug: coding-agent-review-rubric
  • Primary topic: wiki/maps/coding-agent-review-rubric.md
  • Purpose: NotebookLM向けの対話用ソース。KBの6軸レビュー規準を、実装前の計画レビューとして読み直す
  • News angle: X の「新人として計画を書き直す」(catnose99) + /grill-me と GPT-5.6 Sol で実装前の齟齬を grill する (izutorishima)。公式一次ページに 8/24–25 の大型更新は無し

Talking points（3〜5分）

  1. 8月24–25日に公式の大型ドロップは無い。今日のニュースは製品発表ではなく、計画をレビュー可能にする現場の型である。
  2. レビュー rubric は PR の後だけのものではない。同じ6軸を実装前に使うと、設計ドリフトが差分になる前に止まる。
  3. 「スレッドを見ていない新人として計画を書き直す」は、理解可能性という軸そのものだ。
  4. /grill-me と GPT-5.6 Sol は、生成役と採点役を分ける verifier split を、コーディングより前に置く。
  5. 正しさ、爆破半径、単純さ、テスト、リポジトリ適合、理解可能性。この6問が、grill の質問一覧になる。

今日の読み方

knowledge-base-llm の Coding-Agent Review Rubric は、レビューするエージェント、人間、自動レビューが同じ判断軸を使うための、短い運用標準である。KBにはハーネス制御の語彙は多いが、それをコンパクトなレビュー規準にまで落としたノートは、まだ少ない。このマップはその橋である。

昨日までの読み物は、常時稼働のハーネスと、KB＋コードベースのオンボーディングだった。今日はレビュー側に回る。理由は、公式一次ページに新しい大型ドロップが無いからだ。製品面が静かな日は、現場がすでに回している手続きが見える。

X では、catnose99 が計画を「スレッドを一度も見ていない新人」向けに書き直せ、と言っている。izutorishima は、コーディングの前に /grill-me を使い、GPT-5.6 Sol で実装前の齟齬を見つけよ、と言っている。どちらも「もっと賢く書け」ではない。「採点できる対象を先に作れ」である。

今日の問いは「新しいモデルが何を書いたか」ではない。「書く前の計画が、6軸で落ちるかどうか」である。

1. Correctness — 意図は新人にも届くか

変更は意図した要件を満たすか。既存の振る舞いを壊していないか。失敗パスは雑に扱われていないか。

なぜ効くか:

  • 正しさは「動いた」ではなく「頼んだことに対して動いた」
  • エージェントは隣接する正しさを量産できる
  • 計画が曖昧だと、後から正しさを採点できない

今日の角:
スレッドの文脈を共有した人だけが読める計画は、正しさの契約になっていない。新人として書き直すと、「何が完了か」「何を壊してはいけないか」が表に出る。/grill-me の最初の一撃は、実装の好みではなく、この意図の穴である。

対話の種:
「この計画を、会話を見ていない人が読んで、完了条件を同じ言葉で言えるか。」

2. Safety / Blast Radius — 焼くなら差分の前

変更範囲は課題に釣り合うか。危険な副作用、権限ミス、データ破壊、危ない自動化は無いか。巻き戻しと封じ込めは現実的か。

なぜ効くか:

  • 実装後の指摘は、すでに広い差分の上に乗る
  • 爆破半径は、コード量より権限と自動化で決まる
  • 計画段階の縮小は、レビューより安い

今日の角:
公式の新機能が静かな日でも、エージェントは昨日の常時稼働ループの上で書き続けられる。だから grill は「書いてから危なくないか」ではなく、「書いてよい範囲か」を先に聞く。Sol のような強いモデルをここに置くのは、文章を美しくするためではない。範囲を狭めるためである。

対話の種:
「この計画のまま実装してよい範囲と、人間だけが触る範囲は、一文で分かるか。」

3. Maintainability / Simplicity — 複雑な設計を先に落とす

変更は局所的に理解できるか。責務は分かれているか。不要な複雑さを増やしていないか。

なぜ効くか:

  • 生成は複雑さを安く増やせる
  • 単純さは実装後より、設計の選択の時点で安い
  • レビュアーの頭に載らない設計は、後から分割しても遅い

今日の角:
/grill-me が効くのは、実装の好みを議論するからではない。まだ書いていない複雑さを、計画の文章として見える化するからだ。新人向けに書き直せない設計は、すでに複雑すぎる。

対話の種:
「この計画の中心は何をやらないかまで書いているか。それとも全部やる気か。」

4. Test Adequacy — 主張を先にテスト可能にする

テストは変更に釣り合うか。ハッピーパス以外もあるか。主張した振る舞いは、可能な限り決定的チェックで踏まれるか。

なぜ効くか:

  • 決定的チェックは意味のレビューを減らす
  • 「後でテストする」は、計画では未レビューと同じ
  • テスト不能な完了条件は、grill で落ちるべきである

今日の角:
公式ドキュメントに新しいテスト機能は出ていない。だから今日増やすのは製品ではなく、計画の中の検証契約である。grill は「テストを書くつもり」を褒めない。「どのコマンドが赤なら、この計画は失敗か」を聞く。

対話の種:
「この計画が成功したことを、人間の感想ではなく、どのテストが言うのか。」

5. Repo Fit / Harness Fit — 計画はリポジトリの契約か

命名、構造、既存アーキテクチャに合うか。plan や handoff に残った意図と揃っているか。lint、hook、pre-commit、既存のレビューハーネスを尊重しているか。

なぜ効くか:

  • 正しいが場違い、はエージェント特有の失敗
  • ハーネスを迂回する計画は、後から全部赤になる
  • 計画がリポジトリの言葉を使っていないと、実装が別物になる

今日の角:
新人向けの書き直しは、スレッド用語をリポジトリ用語に戻す作業でもある。「昨日のチャットではこう言った」は、handoff ではない。今日の計画が、既存の hook とテストとディレクトリに載るか。それが repo fit である。

対話の種:
「この計画は、リポジトリの今あるレールに乗るか。新しいレールを先に敷こうとしていないか。」

6. Comprehension / Reviewability — 今日のニュースの中心

責任あるレビュアーは、設計と失敗モードを説明できるか。差分は深く見られる大きさか、分割すべきか。生成がテスト、文書、人間のメンタルモデルを追い越していないか。

なぜ効くか:

  • 理解できない変更は、PASS できない
  • レビュー負荷は、エージェント速度の本当の上限である
  • 計画が読めなければ、実装を読めるはずがない

今日の角:
catnose99 の「スレッドを見ていない新人として書け」は、この軸の運用手順である。会話にいた人の記憶を、計画が肩代わりしなければならない。izutorishima の grill は、その書き直した計画を、作った人ではないモデルに渡す。同じスレッドを知っているモデルに「良さそう」と言わせても、理解可能性は測れない。

対話の種:
「この計画を、作ったチャットを知らないモデルが読んで、失敗モードを列挙できるか。」

判定の型

短い rubric は、判定も短くする。

  • PASS
  • PASS WITH NITS
  • NEEDS FIX

出力は、Verdict、Critical issues、Nits、Suggested fix、Confidence。点数表はいらない。カテゴリ判定で、実装してよいか、直してからかを分ける。

/grill-me の出力を、この型に固定すると、Sol の長文が「感想」から「ゲート」に変わる。Confidence が低いなら、実装ではなく、計画の書き直しに戻る。

なぜハーネス部品になるか

  • verifier に採点基準を渡せる
  • レビュー回ごとのドリフトが減る
  • 人間とモデルの意味レビューが比較できる
  • lint やテストを置き換えず、機械が取れない判断だけを担う

KBの言葉では、これは guides-and-sensors を具体的なレビュー道具にしたものであり、machine-checkable invariants の隣に置く inferential control である。Fowler の計算的制御と推論的制御の分け方に乗る。

今日の X の型は、その推論的制御を「PR の後」から「最初のファイル」へ前倒ししている。公式の大型更新が無い日に見えるのは、その前倒しである。

トレードオフ

短い rubric は再利用しやすいが、領域固有の品質を落とす。長い rubric は精密だが、儀式になる。repo-fit は、チームが規約を見直さないと保守的になる。

だから今日の使い方は、6軸を増やすことではない。計画を新人向けに書き、同じ6問で焼き、NEEDS FIX ならコードを開かない。UX、性能、セキュリティが本丸のリポジトリだけ、6番目の隣に1軸足す。

実務のとりはじめ

大きな基盤は要らない。今日からできる最小セット:

  • 実装前に、スレッドを知らない人向けの plan.md を書く
  • その計画を、作ったモデルではない強いモデルに /grill-me する
  • 聞くことはこの6軸。出力は PASS / PASS WITH NITS / NEEDS FIX
  • NEEDS FIX ならコードを触らず、計画を書き直す
  • 通った軸は、PR レビューでも同じ言葉で再採点する

昨日の常時稼働パターンは、計画を残し、検証役を分け、安いチェックを回す話だった。今日の rubric は、その検証役が何を聞くかの台本である。公式が静かな日は、台本を先に固定する日になる。

次に考えるとよさそうな問い

  • 今の計画は、スレッドを見ていない新人に渡せるか？
  • /grill-me の採点役は、計画を書いたモデルと同じか？
  • 6軸のうち、このリポジトリで毎回落ちる軸はどれか？
  • NEEDS FIX のとき、コードではなく計画に戻るルールはあるか？
  • 公式更新が無い日に、現場の手続きだけが先行していないか？
  • 人間だけが PASS を出してよい変更は、どれか？

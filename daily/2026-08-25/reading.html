今日のテーマは「採点できる計画」を先に作ること

knowledge-base-llm の Coding-Agent Review Rubric は、短い運用標準です。レビューするエージェント、人間、自動レビューが、同じ判断軸を使う。KBにはハーネス制御の語彙は多い。それをコンパクトなレビュー規準まで落としたノートは、まだ少ない。このマップはその橋です。

昨日までの読み物は、常時稼働のハーネスと、KB＋コードベースのオンボーディングでした。今日はレビュー側に回ります。公式一次ページに新しい大型ドロップが無いからです。製品面が静かな日は、現場がすでに回している手続きが見えます。

X では、catnose99 が計画を「スレッドを一度も見ていない新人」向けに書き直せ、と言っています。izutorishima は、コーディングの前に /grill-me を使い、GPT-5.6 Sol で設計ドリフトを止めよ、と言っています。どちらも「もっと賢く書け」ではありません。「採点できる対象を先に作れ」です。

ニュースは製品ではなく、前倒しである

レビュー rubric を PR の後だけに置くと、設計ドリフトはすでに広い差分の上に乗っています。今日の現場の型は、同じ6軸を実装前に使います。計画が落ちるなら、コードを開かない。

新人向けの書き直しは、正しさと理解可能性の契約です。会話にいた人の記憶を、計画が肩代わりしなければならない。スレッド用語のままでは、完了条件も壊してはいけないものも、採点できません。

/grill-me と Sol は、verifier split をコーディングより前に置きます。作ったモデルに「良さそう」と言わせても、理解可能性は測れません。強いモデルをここに置くのは、文章を美しくするためではありません。範囲を狭め、複雑さを先に落とし、テスト不能な完了条件を落とすためです。

6軸は grill の質問一覧になる

Correctness は、動いたかではなく、頼んだことに対して動いたか。計画が曖昧だと、後から正しさを採点できません。grill の最初の一撃は、実装の好みではなく、意図の穴です。

Safety / Blast Radius は、書いてから危なくないかではなく、書いてよい範囲か。爆破半径はコード量より、権限と自動化で決まります。公式の新機能が静かな日でも、エージェントは昨日の常時稼働ループの上で書き続けられます。縮小は、レビューより計画の段階が安い。

Maintainability / Simplicity は、まだ書いていない複雑さを文章として見える化します。新人向けに書き直せない設計は、すでに複雑すぎます。Test Adequacy は、「後でテストする」を未レビューとして扱います。どのコマンドが赤なら、この計画は失敗か。

Repo Fit / Harness Fit は、スレッド用語をリポジトリ用語に戻す作業です。「昨日のチャットではこう言った」は handoff ではありません。今日の計画が、既存の hook とテストとディレクトリに載るか。Comprehension / Reviewability が、今日のニュースの中心です。計画が読めなければ、実装を読めるはずがありません。

判定は短く、ゲートにする

短い rubric は、判定も短くします。PASS、PASS WITH NITS、NEEDS FIX。出力は Verdict、Critical issues、Nits、Suggested fix、Confidence。点数表はいりません。

/grill-me の出力をこの型に固定すると、Sol の長文が感想からゲートに変わります。Confidence が低いなら、実装ではなく計画の書き直しに戻る。通った軸は、PR レビューでも同じ言葉で再採点します。

KBの言葉では、これは guides-and-sensors を具体的なレビュー道具にしたものであり、machine-checkable invariants の隣に置く inferential control です。lint やテストを置き換えません。機械が取れない判断だけを担います。

増やさず、前に置く

短い rubric は再利用しやすいが、領域固有の品質を落とします。長い rubric は精密だが、儀式になります。repo-fit は、チームが規約を見直さないと保守的になります。

だから今日の使い方は、6軸を増やすことではありません。計画を新人向けに書き、同じ6問で焼き、NEEDS FIX ならコードを開かない。UX、性能、セキュリティが本丸のリポジトリだけ、6番目の隣に1軸足します。

昨日の常時稼働パターンは、計画を残し、検証役を分け、安いチェックを回す話でした。今日の rubric は、その検証役が何を聞くかの台本です。公式が静かな日は、台本を先に固定する日になります。

よい設計ドリフト対策は、強いモデルに先に書かせることではない。スレッドを知らない人向けの計画を先に残し、書いたモデルではない採点役に6軸で焼かせ、NEEDS FIX ならコードを開かない。

次に考えるとよさそうな問い

  • 今の計画は、スレッドを見ていない新人に渡せるか？
  • /grill-me の採点役は、計画を書いたモデルと同じか？
  • 6軸のうち、このリポジトリで毎回落ちる軸はどれか？
  • NEEDS FIX のとき、コードではなく計画に戻るルールはあるか？
  • 公式更新が無い日に、現場の手続きだけが先行していないか？
  • 人間だけが PASS を出してよい変更は、どれか？

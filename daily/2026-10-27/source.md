# エージェントの自由度を上げる前に、評価と承認をつなぐ

2026年10月27日 JST / KB日次読み物

エージェントSDKは、プロンプトやツールをまとめるだけでなく、どこで動作を検証し、誰が本番適用を承認するかまで設計するための土台になる。CursorのAgent SDK発表（公式日付は10月20日）を、KBのハーネス制御マップ・デプロイゲートマップと読み合わせる。これは製品比較試験ではなく、公開仕様と既存KBから導く運用設計の整理である。[1][2][3]

## 「エージェントをコードにする」の内訳

Cursorの公式changelogによると、`instructions.md`が指示、`tools/`が型付きアクション、`skills/`が必要時に読む手順、`mcp-connections/`が外部ツール、`channels/`が入出力経路を担う。`agent-sdk dev`でローカル実行、`agent-sdk eval`で評価、`agent-sdk deploy`でCursorのホスト基盤に配置できる。自前の基盤での運用も選択肢として挙げている。[1]

この構成は、KBの「事前」「実行中」「実行後」という制御の分類と対応する。指示やツール境界は事前制御、セッションとツール呼び出しの記録は実行中の観測、評価・回帰テストは実行後の検証だ。ただしフォルダに分けただけで権限が安全になったり、評価で未知の障害を網羅できたりするわけではない。[1][2]

## 評価を通ったことと、公開してよいことは別

Agent SDKはGitHub等のPRイベント、Slackメンション、webhook、cronをトリガーとして扱える。評価機能は固定入力で、実行されたツール、入力、応答の形を検査する。`agent-sdk github replay`では既存PRイベントを評価用に再現できる。これらは再現可能な検証経路だが、結果の正しさや本番システムへの変更承認を自動的に保証するものではない。[1]

KBのデプロイゲートマップは、構造チェック、実環境の動作確認、人間によるリスク判断、本番後の観測を別々の層としている。例えばPRの自動修正エージェントなら、ローカルevalが成功しても、差分レビューとCI、リリース前確認を省略しない。承認が必要な書き込み権限は、評価用の読み取り権限と分けるべきだ。後段はKBからの設計提案であり、Cursor製品がそうした運用を強制するという主張ではない。[2][3]

## 小さな導入で確かめること

1. 読み取り専用のPRトリアージを一つ選び、期待する出力と使ってよいツールを明示する。[1][2]
2. 過去のPRイベントを再生し、ツール入力・誤判定・実行時間を記録する。改善の前後を同じ事例で比べる。[1][3]
3. 本番書き込みは独立した権限と人間の承認を必要とし、CI・差分・実環境の結果を確認してから範囲を広げる。[2][3]

結論は「SDKがあれば自律化できる」ではない。再現可能な評価と取り消せる本番操作を、役割と権限の境界でつなぐことが先だ。[1][2][3]
